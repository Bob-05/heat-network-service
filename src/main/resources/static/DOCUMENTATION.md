## 1. Обзор

### 1.1. Назначение

Сервис автоматического построения вариантов подключения перспективных объектов капитального строительства (ОКС) к существующей тепловой сети. Принимает один GeoJSON-файл с исходными данными и возвращает GeoJSON с готовыми маршрутами новых тепловых сетей, тепловыми камерами, техническими узлами и сводкой по вариантам.

### 1.2. Что делает сервис

1. Читает входной GeoJSON и сохраняет объекты в Postgres/PostGIS.
2. Строит граф возможных маршрутов: узлы — ОКС, существующие камеры, точки на существующих сетях, углы препятствий.
3. Для каждой ОКС ищет допустимый маршрут до существующей сети (алгоритм Дейкстры).
4. Группирует рёбра маршрутов, дедуплицирует общие участки, выбирает условный диаметр (ДУ) по расходу и предельной длине.
5. Определяет тип присоединения: существующая камера или новая.
6. Проверяет все пространственные ограничения (горизонтальные и вертикальные).
7. Считает стоимость, штрафы за неподключённые точки и итоговый показатель.
8. Формирует до трёх содержательно отличающихся вариантов и ранжирует их.
9. Записывает результат в GeoJSON согласно разделу 7 ТЗ.

### 1.3. Ключевые особенности

- **Два режима расчёта:** базовый двумерный и дополнительный с учётом глубины. Режимы формируют отдельные наборы вариантов и не объединяются в одно ранжирование.
- **Три варианта на режим:** минимальная длина, минимальная стоимость, минимальный итоговый показатель.
- **Полная проверка ограничений:** запретные зоны, спецпереходы, минимальные углы пересечения, вертикальные просветы.
- **Идемпотентность:** алгоритм не зависит от конкретного набора данных и корректно работает на любом валидном входном GeoJSON.

### 1.4. Что сервис **не** делает

- **Не выполняет реконструкцию** существующих тепловых сетей и камер (отменена в актуальном ТЗ). Существующие объекты используются как есть, их параметры не пересчитываются.
- **Не рассчитывает** текущий расход и резерв пропускной способности существующих сетей.
- **Не создаёт** отдельный объект `tie_in` — присоединение выполняется через тепловую камеру.

## 2. Как работать с сервисом

Этот раздел — пошаговая инструкция для конечного пользователя. Если вы только разворачиваете сервис — начните с раздела [12. Развёртывание](#12-развёртывание).

### 2.1. Общий сценарий работы

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  1. Запуск   │ →  │ 2. Загрузка  │ →  │ 3. Ожидание  │ →  │ 4. Скачать   │
│   сервиса    │    │   GeoJSON    │    │  обработки   │    │  результат   │
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
                                                                   │
                                                                   ▼
                                                          ┌──────────────┐
                                                          │ 5. Анализ    │
                                                          │  на карте    │
                                                          └──────────────┘
```

### 2.2. Шаг 1. Открыть дашборд

После запуска сервиса откройте в браузере:

```
http://localhost:8080/dashboard.html
```

Дашборд содержит четыре вкладки:

| Вкладка | Назначение |
|---|---|
| **Обработка** | Загрузка GeoJSON и запуск задачи |
| **Файлы** | Список загруженных и результирующих файлов |
| **Карта** | Визуализация входных данных и результатов |
| **API Docs** | Встроенная документация OpenAPI |

### 2.3. Шаг 2. Загрузить входной GeoJSON

1. Перейдите на вкладку **Обработка**.
2. Перетащите файл `.geojson` в область загрузки **или** кликните по ней и выберите файл.
3. Проверьте, что в области отображается имя файла и его размер.
4. Нажмите **«Запустить обработку»**.

После этого сервис:
- сохранит файл в `uploads/`,
- вернёт `taskId`,
- запустит асинхронную обработку в фоне.

### 2.4. Шаг 3. Отследить статус

На той же вкладке справа отображается панель **«Статус задачи»**:

| Состояние | Что означает |
|---|---|
| `PROCESSING` | Идёт обработка. Прогресс-бар показывает этапы. |
| `DONE` | Обработка завершена, результат готов. |
| `ERROR` | Произошла ошибка. В поле «Сообщение» — причина. |

Статус обновляется автоматически каждые 1.5 секунды. Дожидаться завершения не обязательно — можно закрыть вкладку и вернуться позже: задача продолжит выполняться на сервере.

### 2.5. Шаг 4. Скачать результат

Когда статус сменится на **«Готово»**:

1. Кнопка **«Скачать результат»** станет активной.
2. Нажмите её — браузер скачает файл `result_<taskId>.geojson`.
3. Кнопка **«Показать на карте»** тоже станет активной — см. шаг 5.

Если обработка завершилась ошибкой, кнопка останется неактивной. Проверьте поле **«Сообщение»** — там будет текст ошибки. Если ошибка непонятна — см. раздел [13. Troubleshooting](#13-troubleshooting).

### 2.6. Шаг 5. Посмотреть результат на карте

Нажмите **«Показать на карте»** на панели статуса. Откроется вкладка **Карта** с загруженным результатом.

Альтернативно:

1. Перейдите на вкладку **Карта**.
2. В выпадающем списке **«Входной»** выберите входной файл (например, `test_input.geojson`).
3. В выпадающем списке **«Результат»** выберите файл с результатом.

**Легенда карты:**

| Цвет / тип | Что обозначает |
|---|---|
| Синяя линия | Новая тепловая сеть (`heat_network`, `laying_method = base`) |
| Оранжевая линия | Специальный проход (`heat_network`, `laying_method = special`) |
| Красная точка | Точка подключения ОКС (`oks_connection_point`) |
| Жёлтая точка | Тепловая камера (`heat_chamber`) |
| Фиолетовая точка | Технический узел (`technical_node`) |

**Взаимодействие:**
- Клик по объекту — всплывающая карточка со всеми атрибутами (`flow_tph`, `diameter`, `length`, `cost` и т.д.).
- Ctrl + колесо мыши — зум.
- Кнопка **«Показать всё»** — подгоняет масштаб под все объекты.

**Важно:** если в результате несколько вариантов (`v1`, `v2`, `v3`), на карте они отображаются **одновременно**. Чтобы различать варианты, ориентируйтесь на атрибут `variant_id` во всплывающей карточке. Для чистого просмотра одного варианта скачайте результат и отфильтруйте по `variant_id` в стороннем GIS-инструменте (QGIS, geojson.io).

### 2.7. Шаг 6. Работа с файлами

Вкладка **Файлы** — это файловый менеджер:

- **Поиск** по имени файла.
- **Скачивание** одного или нескольких файлов (можно выделить чекбоксами и нажать «Скачать выбранные»).
- **Удаление** одного файла, выбранных или всех сразу.
- **Просмотр на карте** — быстрая кнопка «Карта» у каждого файла.

Файлы автоматически обновляются раз в 10 секунд.

### 2.8. Как интерпретировать результат

Результат — это GeoJSON с несколькими типами объектов. Ключевые вещи, на которые стоит смотреть:

**1. `variant_summary` — сводка по варианту.**

Найдите объект с `object_type: "variant_summary"`. Там:

| Поле | О чём говорит |
|---|---|
| `rank` | Место варианта (1 — лучший) |
| `score` | Итоговый показатель. Чем меньше — тем лучше. |
| `calculated_cost` | Итоговая стоимость с учётом штрафов |
| `new_network_length` | Суммарная длина новых сетей |
| `unconnected_oks_ids` | **Список ID неподключённых ОКС.** Если он непустой — часть точек не подключилась, штраф большой. |

**2. `heat_network` — новые участки.**

Каждый участок — это LineString с атрибутами:
- `flow_tph` — расход через участок;
- `diameter` — ДУ;
- `length` — длина;
- `laying_method` — `base` или `special`;
- `cost` — стоимость.

**3. `heat_chamber` — новые камеры.**

Точка с атрибутами `diameter` и `cost`. Существующие камеры в результат **не попадают** — они остаются во входных данных.

**4. `technical_node` — технические узлы.**

Создаются на границах спецпрохода или изменения параметров. Отдельной стоимости не имеют и в `construction_cost` не учитываются.

### 2.9. Как выбрать лучший вариант

Варианты уже ранжированы по `score` (по возрастанию). Наилучший — `rank = 1`.

Если нужно сделать выбор самостоятельно — ориентируйтесь на:
- **Стоимость** (`calculated_cost`) — если приоритет бюджет.
- **Длину** (`new_network_length`) — если приоритет минимальное вмешательство.
- **Количество неподключённых** (`unconnected_oks_ids.length`) — если приоритет полнота решения (0 — идеально).

### 2.10. Работа через API (без UI)

Если вы хотите работать с сервисом программно:

**1. Загрузка файла:**
```bash
curl -X POST http://localhost:8080/api/v1/solve \
     -F "file=@input.geojson"
```

Ответ:
```json
{ "taskId": "abc-123", "status": "PROCESSING", "message": "..." }
```

**2. Проверка статуса:**
```bash
curl http://localhost:8080/api/v1/status/abc-123
```

**3. Скачивание результата:**
```bash
curl -o result.geojson http://localhost:8080/api/v1/result/abc-123
```

**4. Список всех файлов:**
```bash
curl http://localhost:8080/api/v1/files
```

Подробнее — раздел [11. API](#11-api).

### 2.11. Типичные сценарии использования

**Сценарий А: быстрая проверка одного файла**
1. Открыть дашборд.
2. Загрузить файл.
3. Дождаться «Готово».
4. Посмотреть результат на карте.
5. Скачать для детального анализа.

**Сценарий Б: пакетная обработка**
1. Загрузить несколько файлов через UI по очереди или через API.
2. Следить за статусами через `/api/v1/status/{taskId}`.
3. Скачать результаты через `/api/v1/result/{taskId}`.
4. Удалить обработанные файлы через `DELETE /api/v1/files/{type}/{fileName}`.

**Сценарий В: сравнение вариантов**
1. Скачать результат.
2. Открыть в QGIS или geojson.io.
3. Отфильтровать объекты по `variant_id`.
4. Сравнить три варианта по `variant_summary` (score, cost, length, unconnected).

## 3. Архитектура

### 3.1. Слои приложения

```
┌─────────────────────────────────────────────────────┐
│  controller/  →  REST API (TaskController, FileController) │
├─────────────────────────────────────────────────────┤
│  service/     →  Бизнес-логика                      │
│    ├─ TaskService          (оркестрация пайплайна)  │
│    ├─ GeoJsonReaderService (чтение)                 │
│    ├─ GeoJsonWriterService (запись)                 │
│    ├─ RoutingService       (поиск маршрутов)        │
│    ├─ FlowCalculationService (расходы, ДУ, длина)   │
│    ├─ TieInService         (камеры и врезки)        │
│    ├─ CostService          (стоимость, штрафы)      │
│    └─ VariantService       (формирование вариантов) │
├─────────────────────────────────────────────────────┤
│  geometry/    →  Работа с JTS                       │
│    ├─ CoordinateTransformer (WGS84 ↔ UTM37N)        │
│    ├─ GraphBuilder          (построение графа)      │
│    ├─ ObstacleChecker       (проверка ограничений)  │
│    └─ OksPolygonIndex       (индекс полигонов ОКС)  │
├─────────────────────────────────────────────────────┤
│  repository/  →  Spring Data JPA                    │
├─────────────────────────────────────────────────────┤
│  model/       →  JPA-сущности                       │
└─────────────────────────────────────────────────────┘
```

### 3.2. Поток данных

```
GeoJSON (WGS84)
    │
    ▼
GeoJsonReaderService ──► Postgres/PostGIS (geo_objects)
    │
    ▼
TaskService (разделение по типам объектов)
    │
    ├──► oks_connection_point  ──┐
    ├──► heat_chamber          ──┤
    ├──► heat_network          ──┼──► RoutingService
    └──► restriction           ──┘        │
                                          ▼
                              GraphBuilder.buildGraph()
                              (узлы + рёбра, проверка через ObstacleChecker)
                                          │
                                          ▼
                              findRoutes() — Дейкстра по весам
                                          │
                                          ▼
                              FlowCalculationService
                              (дедупликация, ДУ, предельная длина)
                                          │
                                          ▼
                              TieInService (камеры, врезки)
                                          │
                                          ▼
                              CostService (стоимость + штрафы)
                                          │
                                          ▼
                              VariantService (3 варианта, ранжирование)
                                          │
                                          ▼
                              GeoJsonWriterService ──► result_<taskId>.geojson
```

### 3.3. Используемые системы координат

| Этап | CRS | Обоснование |
|---|---|---|
| Входной GeoJSON | EPSG:4326 (WGS84) | Требование ТЗ (раздел 1) |
| Расчёты (длины, расстояния, габариты) | EPSG:32637 (UTM zone 37N) | Требование ТЗ (раздел 1) |
| Выходной GeoJSON | EPSG:4326 (WGS84) | Требование ТЗ (раздел 7) |

Преобразование выполняется `CoordinateTransformer` через библиотеку proj4j.

## 4. Входные данные

Формат — GeoJSON `FeatureCollection` в WGS84 (EPSG:4326). Файл передаётся в `POST /api/v1/solve` как `multipart/form-data`.

### 4.1. Типы объектов

| Объект | `object_type` | Геометрия | Обязательные атрибуты |
|---|---|---|---|
| Источник теплоснабжения | `source` | Point | `id`, `object_type` |
| Существующая тепловая сеть | `heat_network` | LineString | `id`, `object_type`, `diameter` |
| Существующая тепловая камера | `heat_chamber` | Point | `id`, `object_type` |
| Точка подключения ОКС | `oks_connection_point` | Point | `id`, `object_type`, `flow_tph` |
| Пространственное ограничение | `restriction` | LineString / MultiLineString / Polygon / MultiPolygon | `id`, `object_type`, `restriction_type` |

**Особенности:**
- Идентификаторы могут быть строковыми или числовыми. Тип сохраняется при выводе неподключённых ОКС.
- Каждая `oks_connection_point` — самостоятельная цель подключения со своим `flow_tph`.
- Все полигоны ОКС передаются как `restriction` с `restriction_type = "oks"`. Отдельная связь «точка ОКС ↔ полигон ОКС» не задаётся — она определяется геометрически (`OksPolygonIndex`).
- Алгоритм не зависит от конкретного набора данных: координаты, количество объектов и геометрия конкурсного файла не «зашиты» в код.

### 4.2. Пример входного фрагмента

```json
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "properties": {
        "id": "oks_1",
        "object_type": "oks_connection_point",
        "flow_tph": 25.5
      },
      "geometry": {
        "type": "Point",
        "coordinates": [37.6173, 55.7558]
      }
    },
    {
      "type": "Feature",
      "properties": {
        "id": "net_1",
        "object_type": "heat_network",
        "diameter": 200
      },
      "geometry": {
        "type": "LineString",
        "coordinates": [
          [37.6180, 55.7560],
          [37.6200, 55.7570]
        ]
      }
    }
  ]
}
```

## 5. Выходные данные

Формат — GeoJSON `FeatureCollection` в WGS84. Разные варианты различаются атрибутом `variant_id`. Каждый режим (базовый 2D и с учётом глубины) передаётся отдельным GeoJSON-файлом.

### 5.1. Состав выходного файла

| Объект | `object_type` | Геометрия |
|---|---|---|
| Новый участок тепловой сети | `heat_network` | LineString |
| Новая тепловая камера | `heat_chamber` | Point |
| Технический узел | `technical_node` | Point |
| Сводка по варианту | `variant_summary` | null |

### 5.2. Атрибуты `heat_network`

| Атрибут | Формат | Описание |
|---|---|---|
| `id` | string / number | Уникальный идентификатор |
| `object_type` | string | `"heat_network"` |
| `variant_id` | string / number | Идентификатор варианта |
| `start_node_id` | string / number | ID узла в начале LineString |
| `end_node_id` | string / number | ID узла в конце LineString |
| `flow_tph` | number, т/ч | Расчётный расход участка |
| `diameter` | integer, мм | Условный диаметр |
| `length` | number, м | Длина по горизонтальной проекции |
| `laying_method` | string | `"base"` — обычный, `"special"` — спецпроход |
| `depth_start` | number / null | Глубина в начале участка (null в базовом 2D-режиме) |
| `depth_end` | number / null | Глубина в конце участка (null в базовом 2D-режиме) |
| `cost` | number, руб. | Стоимость участка |

**Допустимые узлы** для `start_node_id`/`end_node_id`: `oks_connection_point`, существующая или новая `heat_chamber`, `technical_node`.

Значения должны ссылаться на узлы, **геометрически совпадающие** с концами LineString. Поворот без изменения параметров — внутренняя вершина LineString. Направление записи координат не задаёт направление движения теплоносителя.

### 5.3. Атрибуты `heat_chamber`

| Атрибут | Формат | Описание |
|---|---|---|
| `id` | string / number | Уникальный идентификатор |
| `object_type` | string | `"heat_chamber"` |
| `variant_id` | string / number | Идентификатор варианта |
| `diameter` | integer, мм | Наибольший ДУ примыкающих участков |

## 6. Алгоритм работы

### 6.1. Построение графа (`GraphBuilder`)

Граф — неориентированный, состоит из узлов и рёбер. Каждое ребро — прямая линия между двумя узлами, прошедшая проверку препятствий.

**Типы узлов:**

1. **Целевые узлы** — ОКС и существующие камеры. В графе помечаются `isTarget = true`.
2. **Точки существующих сетей** — существующие `heat_network` разбиваются на равные сегменты с шагом `networkSplitStep` (по умолчанию 5 м). Каждая точка сегмента — узел. Между соседними точками одной сети — рёбра `network-network` с нулевой стоимостью (это уже существующая сеть).
3. **Угловые узлы** препятствий (`cornerNodes`) — берутся вершины выпуклой оболочки препятствия, смещённые наружу на `CORNER_OFFSET_M` (10 м). Помогают трассе «обтекать» запретные зоны с соблюдением нормативных отступов.

**Типы рёбер:**

| Тип | Откуда → Куда | Ограничение по длине |
|---|---|---|
| `network-network` | точка сети → точка сети | сегмент сети |
| `target-network` | ОКС/камера → точка сети | `maxEdgeLength` (5000 м) |
| `target-target` | целевой узел → целевой узел | `maxEdgeLength` |
| `chamber-network` | существующая камера → точка сети | `CHAMBER_TO_NETWORK_MAX_M` (50 м) |
| `visibility` | target/corner → target/corner | `CORNER_CORNER_MAX_M` (300 м) |
| `corner-network` | угловой узел → точка сети | `CORNER_NETWORK_MAX_M` (500 м) |

**Проверка каждого ребра** (`tryBuildEdge` → `isValidEdge`):

1. Ребро не должно пересекать запрещённые препятствия (`oks`, `park`, `social_area`, `prohibited_site`, `water`, `railway`).
2. Расстояние до запрещённых препятствий — не меньше нормативного (5/7/9 м для ОКС, 1 м для остальных).
3. Специальные проходы (`road`, `tram_tracks`, `gas_pipeline`, `power_cable`, `heat_network` — пересечение без врезки) — пересечение допустимо, но с проверкой минимального угла (для дорог и трамвайных путей — ≥ 45°).
4. Внутри разрешённого спецпересечения минимальное горизонтальное расстояние **не проверяется** (разъяснение 7 ТЗ).
5. Исключение для ОКС: если узел находится внутри «своего» полигона ОКС или на его границе (допуск 1 м), ребро к нему разрешено — это финальный прямой участок (разъяснение 3).

**Пространственные индексы** (STRtree) используются для ускорения запросов:
- `obstacleSpatialIndex` — препятствия.
- `networkIndex` — точки сетей.
- `visIndex` — узлы видимости (target + corner).

### 6.2. Поиск маршрутов (`RoutingService`)

Для каждой ОКС запускается **алгоритм Дейкстры** от узла ОКС до ближайшей точки сети. Целевые узлы — все узлы с префиксом `net_`. ОКС запрещены как промежуточные узлы (ТЗ п.2.1: разветвления только в камерах).

**Три веса:**

| Вес | Формула | Когда применяется |
|---|---|---|
| `LENGTH` | длина ребра | минимизация длины |
| `COST` | стоимость ребра | минимизация стоимости |
| `SCORE` | `0.7·(cost / 25e6) + 0.3·(length / 100)` | минимизация итогового показателя |

**Важно:** граф строится **один раз** (`buildGraphOnce`), затем для каждого веса запускается `findRoutes`. Это ключевая оптимизация — построение графа самое дорогое.

### 6.3. Расчёт расходов и ДУ (`FlowCalculationService`)

**Дедупликация общих участков.** Каждое ребро группируется по неориентированному ключу:

```
key = min(fromId, toId) + "|" + max(fromId, toId)
```

Все маршруты, проходящие через ребро, вносят свой `oksFlowTph` в суммарный расход. Так общий участок разветвлённой сети учитывается один раз.

**Выбор ДУ.** Для каждого уникального ребра:

```
расход = сумма flow_tph всех ОКС, для которых ребро входит в маршрут
макс. длина пути = максимум totalLength среди маршрутов через ребро
```

ДУ выбирается из таблицы 1 (п.7.1): первый, у которого `пропускная способность >= расход` И `предельная длина >= макс. длина пути`.

**Правило неуменьшения ДУ.** По направлению от точки подключения к месту присоединения ДУ новой сети не должен уменьшаться. Реализовано итеративно: если у ребра `A→B` ДУ меньше, чем максимальный ДУ всех входящих в `A` рёбер — ДУ повышается, и цикл повторяется до стабилизации.

**Правило смены отсчёта предельной длины.** Предельная длина проверяется отдельно по каждому непрерывному пути. Общий участок разветвлённой сети учитывается в каждом соответствующем пути. Длины параллельных ветвей не суммируются. Камера или технический узел без изменения ДУ новый отсчёт не начинают. При изменении ДУ начинается новый отсчёт.

### 6.4. Определение врезок и камер (`TieInService`)

Для каждого маршрута:

1. Ищется существующая камера в радиусе 10 м от конечной точки маршрута.
2. Проверяется, что после подключения к камере будет **не более 4 примыканий** (разъяснение 12).
3. Если условие выполнено — используется существующая камера. Стоимость одной врезки — 5 000 000 руб. за каждый новый линейный участок, заканчивающийся в ней.
4. Иначе — создаётся новая камера в конечной точке, стоимость по таблице 3.2 (по наибольшему ДУ примыкающих участков).

**Динамический учёт.** Новые примыкания, созданные в рамках текущего расчёта, учитываются при проверке лимита ≤ 4 для последующих ОКС.

**Объединение новых камер.** Если две новые камеры оказались в одной точке (с точностью 1 м), они объединяются в одну с максимальным ДУ.

**Существующие примыкания.** Подсчёт `countExistingTieIns`:
- Вершина существующей сети, совпадающая с камерой (допуск 1 м) → +1.
- Существующая линия, проходящая через камеру и разделённая ею на две части → +2.

**Отдельный объект `tie_in` не формируется.** Присоединение новой сети к существующей выполняется через тепловую камеру.

### 6.5. Формирование вариантов (`VariantService`)

Формируются три варианта с разными весами Дейкстры:

| Вариант | Вес | Логика |
|---|---|---|
| `vL` | LENGTH | минимальная длина |
| `vC` | COST | минимальная стоимость |
| `vS` | SCORE | минимальный итоговый показатель |

**Дедупликация.** Варианты, у которых совпадают все рёбра (`buildSignature`), отсеиваются. Небольшое смещение одной и той же трассы отдельным вариантом не считается.

**Ранжирование.** Оставшиеся варианты сортируются по `score` (по возрастанию). `rank = 1` — лучший. `variant_id` переприсваивается: `v1`, `v2`, `v3`.

**Ограничение:** сервис возвращает **до трёх** содержательно отличающихся вариантов на каждый режим.

### 6.6. Проверка углов поворота и минимальной длины прямого участка

Изменение направления в одной точке допускается до 90° включительно. В пределах от 0° до 90° угол может быть произвольным. Отдельное удорожание поворота не применяется. Минимальная длина прямого участка между соседними поворотами отдельно не задаётся. Трасса не содержит необоснованных мелких изломов, зигзагов и ступенчатых фрагментов — это обеспечивается структурой графа (крупные шаги, углы препятствий смещены наружу).

### 6.7. Углы пересечения ограничений

Для линейной геометрии угол пересечения определяется относительно линии ограничения. Для полигональной геометрии — в точке входа специального участка относительно границы полигона, через который проходит трасса. Если для типа ограничения задан минимальный угол (дороги, трамвайные пути), он соблюдается.

### 6.8. Наложение специальных проходов

Если специальные проходы накладываются друг на друга:
- На общем фрагменте должны выполняться все геометрические требования соответствующих ограничений.
- Для расчёта стоимости применяется **наибольший** из соответствующих коэффициентов `K_спец`. Коэффициенты не суммируются и не перемножаются.
- При изменении набора пересекаемых ограничений начинается новый участок.

### 7.2. Выбор ДУ

Для каждого участка новой сети определяется расчётный расход = сумма `flow_tph` всех ОКС, расположенных **далее по этому участку** (в направлении к сети).

ДУ выбирается по двум критериям одновременно:
1. Пропускная способность ≥ расчётный расход.
2. Предельная длина ≥ длина непрерывного пути, включающего этот участок.

Если минимальный по расходу ДУ не проходит по длине — берётся следующий, удовлетворяющий обоим. Произвольное завышение не допускается.

### 7.3. Предельная длина

Проверяется **отдельно по каждому непрерывному пути**. Общий участок разветвлённой сети учитывается в каждом соответствующем пути. Длины параллельных ветвей между собой **не суммируются**.

- Камера без изменения ДУ — новый отсчёт **не** начинает.
- Технический узел без изменения ДУ — новый отсчёт **не** начинает.
- Изменение ДУ — начинается новый отсчёт.

### 7.4. Присоединение к существующей сети

Всегда через тепловую камеру.

**Существующая камера** используется, если:
- Точка присоединения не далее 10 м от существующей `heat_chamber`.
- После подключения к камере будет примыкать не более 4 линейных участков.

Иначе создаётся **новая камера** в выбранной точке существующей сети. Отдельный геообъект `tie_in` **не формируется**. Отдельное минимальное расстояние между существующей и новой камерой не задаётся.

Если условию использования существующей камеры соответствуют несколько камер, выбирается одна из них.

### 7.5. Стоимость камер и врезок (Таблица 3.2 ТЗ)

| Наибольший ДУ примыкающих участков | Стоимость новой камеры, руб. |
|---|---|
| 50–200 | 3 000 000 |
| 250–500 | 5 000 000 |
| 600–1000 | 8 000 000 |
| 1200–1400 | 12 000 000 |

**Врезка в существующую камеру** — 5 000 000 руб. за каждый новый линейный участок, заканчивающийся в ней.

Стоимость новой камеры **включает** присоединение к существующей сети. Отдельная стоимость врезки при строительстве новой камеры не добавляется.

### 7.6. Стоимость участков

```
Обычный участок:      C_уч = L · c_нов(ДУ) · K_гл
Специальный участок:  C_уч = L · c_нов(ДУ) · K_гл · K_спец
```

где:
- `L` — длина по горизонтальной проекции в EPSG:32637, м.
- `c_нов(ДУ)` — стоимость строительства, руб./м (таблица 1).
- `K_гл` — коэффициент глубины (см. раздел 9).
- `K_спец` — коэффициент спецпрохода (таблица 2).

Если параметры по длине меняются, стоимость соответствующих частей рассчитывается отдельно.

### 7.7. Расчёт итоговой стоимости

```
construction_cost  = сумма стоимости участков
                   + стоимость новых камер
                   + стоимость врезок в существующие камеры

unconnected_penalty = Σ (100 000 000 + 500 000 · flow_tph)  по неподключённым

calculated_cost    = construction_cost + unconnected_penalty
```

### 8.2. Расчётный габарит

Линия новой сети в GeoJSON — это **ось пары труб**. Для проверки расстояний учитывается расчётная ширина из таблицы 1:

```
внешняя граница сети = ось ± (ширина / 2)
```

Для полигонального ограничения расстояние измеряется от границы полигона до внешней границы габарита сети. Для линейного — от геометрии ограничения до внешней границы.

Если у ограничения задан собственный габарит, расстояние определяется между внешними границами двух габаритов. Условные габариты:
- Газопровод: 0,40 × 0,40 м, глубина до верха — 2,8 м.
- Силовой кабель: 0,20 × 0,20 м, глубина — 2,7 м.
- Существующая тепловая сеть: габарит по таблице 1, глубина — 3,0 м.

### 8.3. Специальные проходы

Специальный проход выполняется **одним прямым участком**. На границах спецпрохода участок делится. Если граница не совпадает с тепловой камерой или точкой подключения ОКС — создаётся `technical_node`.

**Внутри разрешённого специального пересечения минимальное горизонтальное расстояние не проверяется.** При прохождении рядом с ограничением (без пересечения) расстояние измеряется по правилам п.8.2.

**Наложение спецпроходов.** Если спецпроходы пересекаются:
- На общем фрагменте выполняются все геометрические требования.
- Для стоимости применяется **наибольший** из коэффициентов `K_спец`. Коэффициенты не суммируются и не перемножаются.
- На границах общего фрагмента начинается новый участок.
- Каждое отдельное пересечение одного и того же объекта считается отдельным специальным проходом.

### 8.4. Исключение для ОКС

Полигон `restriction_type = "oks"` — непроходимое препятствие с отступом по таблице. **Исключение:** для полигона, содержащего собственную `oks_connection_point`, допускается один финальный прямой участок от ближайшей к точке границы полигона до самой точки.

Требование отступа к собственному полигону на этот участок **не распространяется**, включая часть в зоне отступа перед границей. Остальные ограничения продолжают действовать.

Если в одном полигоне несколько `oks_connection_point` — каждая рассматривается как самостоятельная цель подключения и имеет собственный `flow_tph`. Отдельная связь точки подключения с полигоном ОКС не требуется.

### 8.5. Типы ограничений из таблицы 2

В обязательной части решения используются типы ограничений, перечисленные в таблице 2 технического приложения. Поддержка иных `restriction_type` не является обязательной.

## 9. Дополнительный режим с учётом глубины

### 9.1. Общие принципы

Базовый двумерный расчёт сохраняется. Расчёт с глубиной выполняется как **отдельный режим** и формирует **отдельный набор вариантов**. Маршрут может быть построен заново и не обязан совпадать с двумерным вариантом. Результаты двух режимов **не объединяются** в одно ранжирование.

Z-координаты в GeoJSON не требуются. Вертикальное положение задаётся атрибутами `depth_start` и `depth_end` в начале и конце участка.

### 9.2. Параметры глубины

- Обычная глубина до верхней границы расчётного габарита новой сети — **3,0 м**.
- Минимальная глубина — **0,7 м**.
- Максимальная глубина — не задаётся.
- Дискретный шаг по глубине — не задаётся.
- Максимальный уклон — **0,10 м/м**.
- Для изменения глубины на 1 м требуется не менее 10 м по горизонтали.
- Принимается условная горизонтальная поверхность земли.

### 9.3. Профиль глубины

Если глубину необходимо изменить, профиль состоит из:
1. Участка спуска или подъёма.
2. Участка на постоянной глубине.
3. При необходимости — участка возврата.

Между близкими препятствиями допускается сохранять изменённую глубину, если все требования к пересечениям выполняются.

### 9.4. Коэффициент глубины K_гл

При `h ≤ 3,0 м`:

```
K_гл = 1
```

При `h > 3,0 м`:

```
K_гл = 1 + 0,10 · (h − 3)
```

где `h` — глубина до верхней границы расчётного габарита, м.

На участке равномерного спуска или подъёма для стоимости используется среднее арифметическое `K_гл` в начале и конце.

### 9.5. Технические узлы на профиле

Если участок пересекает глубину 3,0 м, в этой точке создаётся технический узел (`technical_node`) и участок делится.

### 9.6. Расчёт стоимости и длины

Для расчёта стоимости и предельной длины используется **длина по горизонтальной проекции** в EPSG:32637.

## 10. Стоимость и ранжирование

### 10.1. Формула ранжирования

```
S = 0,7 · (C / 25 000 000) + 0,3 · (L / 100)
```

где:
- `C` = `calculated_cost`, руб.
- `L` = `new_network_length`, м.

**Чем меньше S — тем лучше вариант.**

### 10.2. Штраф за неподключённые точки

```
Ш = 100 000 000 + 500 000 · G
```

где `G` = `flow_tph` точки подключения, т/ч.

**Неподключение допускается только если сервис не нашёл допустимый маршрут** при соблюдении правил ТЗ. Намеренный отказ от технически доступного подключения для улучшения итогового показателя **не допускается**.

### 10.3. Разделение режимов

Базовый 2D-режим и режим с глубиной формируют **отдельные наборы вариантов**. Результаты двух режимов не объединяются в одно ранжирование.

### 10.4. Количество вариантов

В каждом режиме сервис может вернуть **до трёх содержательно отличающихся вариантов**. Небольшое смещение одной и той же трассы отдельным вариантом не считается.

## 13. Troubleshooting

### 13.1. Сервис вернул пустой результат

**Симптом:** в `variant_summary` нет новых `heat_network`, все ОКС в `unconnected_oks_ids`.

**Возможные причины:**
- Все ОКС окружены запретными препятствиями и маршрут невозможен при соблюдении правил ТЗ.
- `flow_tph` ОКС превышает пропускную способность максимального ДУ (22 501,9 т/ч) — сервис не может подобрать допустимый ДУ и вынужден отказать в подключении.
- Длина пути до сети превышает предельную длину даже для ДУ 1400 мм (11 276 м).

**Что проверить:** логи `TaskService` и `RoutingService`. Ищите сообщения о невозможности найти маршрут или подобрать ДУ.

### 13.2. ОКС подключился, но маршрут выглядит неоптимально

**Симптом:** трасса обходит препятствие с большим крюком.

**Возможные причины:**
- Углы препятствий смещены наружу на 10 м — для узких длинных препятствий это может давать избыточное смещение.
- Другие маршруты оказались заблокированы запретными зонами.

**Что проверить:** откройте результат на карте, включите слой входных ограничений. Возможно, короткий путь проходит через запретную зону.

### 13.3. Ошибка подключения к БД

**Симптом:** приложение не стартует, `Connection refused` к `localhost:5432`.

**Причина:** не запущен Docker-контейнер с Postgres.

**Решение:**
```bash
docker compose up -d db
docker ps   # убедиться, что heat-network-db в статусе Up
```

### 13.4. Ошибка при чтении входного GeoJSON

**Симптом:** задача завершилась со статусом `ERROR`, в логе `"Ошибка парсинга feature"`.

**Возможные причины:**
- Отсутствует `object_type` в properties.
- Геометрия содержит `null` в координатах.
- Неподдерживаемый тип геометрии.

**Что проверить:** валидность GeoJSON через [geojson.io](https://geojson.io). Убедиться, что все фичи имеют `properties.object_type`.

### 13.5. Некорректные длины в результате

**Симптом:** `length` участка не совпадает с ожидаемым.

**Причина:** длина считается в EPSG:32637, а не в градусах WGS84. Это правильно по ТЗ, но при ручной проверке через GIS-инструменты легко ошибиться.

**Что проверить:** `CoordinateTransformer` — все геометрии перед расчётом конвертируются в UTM37N.

### 13.6. Стоимость сильно завышена

**Симптом:** `calculated_cost` на порядок больше ожидаемого.

**Возможные причины:**
- Большая часть ОКС не подключилась — штраф `100 000 000 + 500 000 · G` за каждую точку даёт огромную прибавку.
- `K_спец` неправильно применён.

**Что проверить:** `unconnected_oks_ids` в `variant_summary`, `unconnected_penalty`.

### 13.7. Задача висит в `PROCESSING` слишком долго

**Симптом:** статус не меняется, результат не появляется.

**Возможные причины:**
- Очень большой входной файл (много объектов или сложная геометрия).
- Построение графа зависит от количества узлов.

**Что проверить:** логи `TaskService` — там есть тайминги построения графа, расчёта участков и формирования вариантов. Если время растёт непропорционально — рассмотреть уменьшение `max-edge-length` или `network-split-step`.

### 13.8. На карте отображаются все варианты сразу

**Симптом:** при выборе файла результата на карте видны все три варианта (`v1`, `v2`, `v3`) одновременно.

**Причина:** GeoJSON-файл содержит объекты всех вариантов, и OpenLayers читает их одним слоем.

**Решение:** для чистого просмотра одного варианта скачайте результат и отфильтруйте объекты по `variant_id` в QGIS или geojson.io.

### 13.9. Реконструкция существующей сети не выполняется

**Симптом:** ожидалось, что сервис пересчитает ДУ существующих участков, но в результате их нет.

**Причина:** это соответствует ТЗ. В актуальной расчётной модели реконструкция существующих тепловых сетей и камер **не выполняется**. Существующие объекты используются как есть, их текущий расход и резерв пропускной способности не определяются.
