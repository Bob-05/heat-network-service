## 1. Обзор

### 1.1. Назначение

Сервис автоматического построения вариантов подключения перспективных объектов капитального строительства (ОКС) к существующей тепловой сети. Принимает один GeoJSON-файл с исходными данными и возвращает GeoJSON с готовыми маршрутами новых тепловых сетей, тепловыми камерами, техническими узлами и сводкой по вариантам.

### 1.2. Что делает сервис

1. Читает входной GeoJSON и сохраняет объекты в Postgres/PostGIS.
2. Строит граф возможных маршрутов: узлы — ОКС, существующие камеры, точки на существующих сетях, углы препятствий.
3. Для каждой ОКС ищет допустимый маршрут до существующей сети (алгоритм Дейкстры).
4. Группирует рёбра маршрутов, дедуплицирует общие участки, выбирает условный диаметр (ДУ) по расходу и предельной длине.
5. Определяет тип присоединения: существующая камера или новая.
6. Проверяет все пространственные ограничения (горизонтальные и вертикальные).
7. Считает стоимость, штрафы за неподключённые точки и итоговый показатель.
8. Формирует до трёх содержательно отличающихся вариантов и ранжирует их.
9. Записывает результат в GeoJSON согласно разделу 7 ТЗ.

### 1.3. Ключевые особенности

- **Базовый двумерный режим** — основной. Дополнительный режим с глубиной (раздел 5 ТЗ) не является обязательным и в текущей версии не реализован.
- **Три варианта на режим:** минимальная длина, минимальная стоимость, минимальный итоговый показатель.
- **Полная проверка ограничений:** запретные зоны, спецпереходы, минимальные углы пересечения.
- **Идемпотентность:** алгоритм не зависит от конкретного набора данных и корректно работает на любом валидном входном GeoJSON.

### 1.4. Что сервис **не** делает

- **Не выполняет реконструкцию** существующих тепловых сетей и камер (разъяснение 14).
- **Не рассчитывает** текущий расход и резерв пропускной способности существующих сетей.
- **Не создаёт** отдельный объект `tie_in` (разъяснение 13).

## 2. Как работать с сервисом

### 2.1. Общий сценарий работы

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  1. Запуск   │ →  │ 2. Загрузка  │ →  │ 3. Ожидание  │ →  │ 4. Скачать   │
│   сервиса    │    │   GeoJSON    │    │  обработки   │    │  результат   │
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
                                                                   │
                                                                   ▼
                                                          ┌──────────────┐
                                                          │ 5. Анализ    │
                                                          │  на карте    │
                                                          └──────────────┘
```

### 2.2. Шаг 1. Открыть дашборд

```
http://localhost:8080/dashboard.html
```

Дашборд содержит пять вкладок:

| Вкладка | Назначение |
|---|---|
| **Обработка** | Загрузка GeoJSON и запуск задачи |
| **Файлы** | Список загруженных и результирующих файлов |
| **Карта** | Визуализация входных данных и результатов |
| **API Docs** | Встроенная документация OpenAPI |
| **Документация** | Развёрнутый справочник |

### 2.3. Шаг 2. Загрузить входной GeoJSON

1. Перейдите на вкладку **Обработка**.
2. Перетащите файл `.geojson` в область загрузки **или** кликните по ней и выберите файл.
3. Нажмите **«Запустить обработку»**.

Сервис сохранит файл в `uploads/`, вернёт `taskId` и запустит асинхронную обработку.

### 2.4. Шаг 3. Отследить статус

| Состояние | Что означает |
|---|---|
| `PROCESSING` | Идёт обработка. |
| `DONE` | Обработка завершена, результат готов. |
| `ERROR` | Произошла ошибка. В поле «Сообщение» — причина. |

Статус обновляется автоматически каждые 1.5 секунды.

### 2.5. Шаг 4. Скачать результат

Когда статус сменится на **«Готово»** — кнопка **«Скачать результат»** станет активной. Браузер скачает `result_<taskId>.geojson`.

### 2.6. Шаг 5. Посмотреть результат на карте

Нажмите **«Показать на карте»**. Откроется вкладка **Карта** с загруженным результатом.

**Легенда карты:**

| Цвет / тип | Что обозначает |
|---|---|
| Синяя линия | Новая тепловая сеть (`heat_network`, `laying_method = base`) |
| Оранжевая линия | Специальный проход (`heat_network`, `laying_method = special`) |
| Жёлтая точка | Новая тепловая камера (`heat_chamber`) |
| Фиолетовая точка | Технический узел (`technical_node`) |

**Взаимодействие:**
- Клик по объекту — всплывающая карточка со всеми атрибутами.
- Ctrl + колесо мыши — зум.
- Кнопка **«Показать всё»** — подгоняет масштаб под все объекты.

**Важно:** если в результате несколько вариантов (`v1`, `v2`, `v3`), на карте они отображаются **одновременно**. Для чистого просмотра одного варианта скачайте результат и отфильтруйте по `variant_id` в QGIS или geojson.io.

### 2.7. Шаг 6. Работа с файлами

Вкладка **Файлы**: поиск, скачивание, удаление. Обновление раз в 10 секунд.

### 2.8. Как интерпретировать результат

**1. `variant_summary` — сводка по варианту.**

| Поле | О чём говорит |
|---|---|
| `rank` | Место варианта (1 — лучший) |
| `score` | Итоговый показатель. Чем меньше — тем лучше. |
| `calculated_cost` | Итоговая стоимость с учётом штрафов |
| `new_network_length` | Суммарная длина новых сетей |
| `unconnected_oks_ids` | **Список ID неподключённых ОКС.** Если он непустой — часть точек не подключилась. |

**2. `heat_network` — новые участки.**

Каждый участок — LineString с атрибутами `flow_tph`, `diameter`, `length`, `laying_method`, `cost`.

**3. `heat_chamber` — новые камеры.**

Точка с атрибутами `diameter` и `cost`. Существующие камеры в результат **не попадают**.

**4. `technical_node` — технические узлы.**

Создаются на границах спецпрохода. Отдельной стоимости не имеют.

### 2.9. Как выбрать лучший вариант

Варианты уже ранжированы по `score` (по возрастанию). Наилучший — `rank = 1`.

### 2.10. Работа через API

```bash
# Загрузка
curl -X POST http://localhost:8080/api/v1/solve -F "file=@input.geojson"

# Статус
curl http://localhost:8080/api/v1/status/abc-123

# Результат
curl -o result.geojson http://localhost:8080/api/v1/result/abc-123
```

## 4. Входные данные

Формат — GeoJSON `FeatureCollection` в WGS84 (EPSG:4326). Файл передаётся в `POST /api/v1/solve` как `multipart/form-data`.

### 4.1. Типы объектов

| Объект | `object_type` | Геометрия | Обязательные атрибуты |
|---|---|---|---|
| Источник теплоснабжения | `source` | Point | `id`, `object_type` |
| Существующая тепловая сеть | `heat_network` | LineString | `id`, `object_type`, `diameter` |
| Существующая тепловая камера | `heat_chamber` | Point | `id`, `object_type` |
| Точка подключения ОКС | `oks_connection_point` | Point | `id`, `object_type`, `flow_tph` |
| Пространственное ограничение | `restriction` | LineString / MultiLineString / Polygon / MultiPolygon | `id`, `object_type`, `restriction_type` |

**Особенности:**
- Идентификаторы могут быть строковыми или числовыми. Тип сохраняется при выводе `unconnected_oks_ids`.
- Каждая `oks_connection_point` — самостоятельная цель со своим `flow_tph`.
- Все полигоны ОКС передаются как `restriction` с `restriction_type = "oks"`. Связь с точкой ОКС определяется геометрически (`OksPolygonIndex`).
- Алгоритм не зависит от конкретного набора данных.

### 4.2. Пример входного фрагмента

```json
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "properties": {
        "id": "oks_1",
        "object_type": "oks_connection_point",
        "flow_tph": 25.5
      },
      "geometry": {
        "type": "Point",
        "coordinates": [37.6173, 55.7558]
      }
    },
    {
      "type": "Feature",
      "properties": {
        "id": "net_1",
        "object_type": "heat_network",
        "diameter": 200
      },
      "geometry": {
        "type": "LineString",
        "coordinates": [
          [37.6180, 55.7560],
          [37.6200, 55.7570]
        ]
      }
    }
  ]
}
```

## 5. Выходные данные

Формат — GeoJSON `FeatureCollection` в WGS84. Разные варианты различаются `variant_id`.

### 5.1. Состав выходного файла

| Объект | `object_type` | Геометрия |
|---|---|---|
| Новый участок тепловой сети | `heat_network` | LineString |
| Новая тепловая камера | `heat_chamber` | Point |
| Технический узел | `technical_node` | Point |
| Сводка по варианту | `variant_summary` | null |

### 5.2. Атрибуты `heat_network`

| Атрибут | Формат | Описание |
|---|---|---|
| `id` | string / number | Уникальный идентификатор |
| `object_type` | string | `"heat_network"` |
| `variant_id` | string / number | Идентификатор варианта |
| `start_node_id` | string / number | ID узла в начале LineString |
| `end_node_id` | string / number | ID узла в конце LineString |
| `flow_tph` | number, т/ч | Расчётный расход участка |
| `diameter` | integer, мм | Условный диаметр |
| `length` | number, м | Длина по горизонтальной проекции |
| `laying_method` | string | `"base"` — обычный, `"special"` — спецпроход |
| `depth_start` | number / null | Глубина в начале участка (null в базовом 2D-режиме) |
| `depth_end` | number / null | Глубина в конце участка (null в базовом 2D-режиме) |
| `cost` | number, руб. | Стоимость участка |

**Допустимые узлы** для `start_node_id`/`end_node_id`: `oks_connection_point`, существующая или новая `heat_chamber`, `technical_node`.

Значения должны ссылаться на узлы, **геометрически совпадающие** с концами LineString. Поворот без изменения параметров — внутренняя вершина LineString. Направление записи координат не задаёт направление движения теплоносителя.

### 5.3. Атрибуты `heat_chamber`

| Атрибут | Формат | Описание |
|---|---|---|
| `id` | string / number | Уникальный идентификатор |
| `object_type` | string | `"heat_chamber"` |
| `variant_id` | string / number | Идентификатор варианта |
| `diameter` | integer, мм | Наибольший ДУ примыкающих участков |
| `cost` | number, руб. | Стоимость новой камеры |

Существующие камеры в результат **не попадают** — они остаются во входных данных.

### 5.4. Атрибуты `technical_node`

`technical_node` имеет только обязательные `id`, `object_type`, `variant_id`. Дополнительных атрибутов нет. Технический узел **не является тепловой камерой**, не используется для разветвления и **отдельной стоимости не имеет** — в `construction_cost` не учитывается.

### 5.5. Атрибуты `variant_summary`

| Атрибут | Формат | Описание |
|---|---|---|
| `rank` | integer | Место варианта (1 — лучший) |
| `construction_cost` | number, руб. | Стоимость строительства |
| `chamber_construction_cost` | number, руб. | Стоимость новых камер |
| `existing_chamber_tie_in_count` | integer | Количество врезок в существующие камеры |
| `existing_chamber_tie_in_cost` | number, руб. | Стоимость врезок |
| `unconnected_penalty` | number, руб. | Штраф за неподключённые точки |
| `calculated_cost` | number, руб. | Итоговая стоимость |
| `new_network_length` | number, м | Суммарная длина новых участков |
| `score` | number | Итоговый показатель |
| `unconnected_oks_ids` | array | ID неподключённых ОКС (тип сохраняется) |

### 5.6. Дополнительные свойства

Дополнительные `properties` допускаются и при проверке обязательной части решения игнорируются.

## 6. Алгоритм работы

### 6.1. Построение графа (`GraphBuilder`)

Граф — неориентированный, состоит из узлов и рёбер. Каждое ребро — прямая линия между двумя узлами, прошедшая проверку препятствий.

**Типы узлов:**

1. **Целевые узлы** — ОКС и существующие камеры.
2. **Точки существующих сетей** — существующие `heat_network` разбиваются на равные сегменты с шагом `networkSplitStep` (по умолчанию 5 м). Между соседними точками — рёбра `network-network` с нулевой стоимостью.
3. **Угловые узлы** препятствий (`cornerNodes`) — вершины выпуклой оболочки препятствия, смещённые наружу на `cornerOffset` (10 м).

**Типы рёбер:**

| Тип | Откуда → Куда | Ограничение по длине |
|---|---|---|
| `network-network` | точка сети → точка сети | сегмент сети |
| `target-network` | ОКС/камера → точка сети | `maxEdgeLength` |
| `target-target` | целевой узел → целевой узел | `maxEdgeLength` |
| `chamber-network` | существующая камера → точка сети | `chamberToNetworkMax` |
| `visibility` | target/corner → target/corner | `cornerCornerMax` |
| `corner-network` | угловой узел → точка сети | `cornerNetworkMax` |

**Проверка каждого ребра** (`isValidEdge`):

1. Не пересекать запрещённые препятствия (`oks`, `park`, `social_area`, `prohibited_site`, `water`, `railway`).
2. Расстояние до запрещённых препятствий — не меньше нормативного (5/7/9 м для ОКС, 1 м для остальных).
3. Специальные проходы (`road`, `tram_tracks`, `gas_pipeline`, `power_cable`, `heat_network` — пересечение без врезки) — пересечение допустимо, но с проверкой минимального угла (для дорог и трамвайных путей — ≥ 45°).
4. Внутри разрешённого спецпересечения минимальное горизонтальное расстояние **не проверяется** (разъяснение 7).
5. Исключение для ОКС: если узел находится внутри «своего» полигона ОКС или на его границе (допуск 1 м), ребро к нему разрешено — это финальный прямой участок (разъяснение 3).

**Пространственные индексы** (STRtree): `obstacleSpatialIndex`, `networkIndex`, `visIndex`.

### 6.2. Поиск маршрутов (`RoutingService`)

Для каждой ОКС запускается **алгоритм Дейкстры** от узла ОКС до ближайшей точки сети. Целевые узлы — все узлы с префиксом `net_`. ОКС запрещены как промежуточные узлы (разветвления только в камерах, п.2.1).

**Три веса:**

| Вес | Формула | Когда применяется |
|---|---|---|
| `LENGTH` | длина ребра | минимизация длины |
| `COST` | стоимость ребра | минимизация стоимости |
| `SCORE` | `0.7·(cost / 25e6) + 0.3·(length / 100)` | минимизация итогового показателя |

Граф строится **один раз** (`buildGraphOnce`), затем для каждого веса запускается `findRoutes`.

### 6.3. Расчёт расходов и ДУ (`FlowCalculationService`)

**Дедупликация общих участков.** Каждое ребро группируется по неориентированному ключу:

```
key = min(fromId, toId) + "|" + max(fromId, toId)
```

Все маршруты, проходящие через ребро, вносят свой `oksFlowTph` в суммарный расход.

**Выбор ДУ.** Начальный ДУ — минимальный по расходу. Затем итеративно:

1. Для каждого маршрута режется непрерывный под-путь с **одинаковым расходом** (разъяснение 1: «На участке с неизменным расчётным расходом выбранный ДУ сохраняется по всей длине»).
2. Если длина под-пути превышает предельную для текущего ДУ — ДУ повышается для **всех рёбер этого под-пути** до минимально подходящего.
3. Итерации повторяются до стабилизации.

**Правило неуменьшения ДУ.** По направлению от ОКС к месту присоединения ДУ не должен уменьшаться. Реализовано итеративно с учётом ориентации рёбер маршрута.

### 6.4. Определение врезок и камер (`TieInService`)

Для каждого маршрута:

1. Ищется существующая камера в радиусе 10 м от конечной точки.
2. Проверяется, что после подключения к камере будет **не более 4 примыканий** (разъяснение 12).
3. Если условие выполнено — используется существующая камера. Стоимость — 5 000 000 руб. за каждый новый линейный участок, заканчивающийся в ней.
4. Иначе — создаётся новая камера в конечной точке, стоимость по таблице 3.2.

**Junction-камеры.** Узел со степенью ≥ 3, не являющийся ОКС или существующей камерой, повышается до новой `heat_chamber` (разветвления только в камерах, п.2.1). При выборе существующей камеры рядом проверяется лимит ≤ 4 с учётом существующих примыканий и степени развилки.

**Объединение новых камер.** Если две новые камеры оказались в одной точке (точность 1 м), они объединяются в одну с максимальным ДУ.

**Отдельный объект `tie_in` не формируется.** Присоединение — через тепловую камеру (разъяснение 13).

### 6.5. Формирование вариантов (`VariantService`)

Три варианта с разными весами Дейкстры:

| Вариант | Вес | Логика |
|---|---|---|
| `vL` | LENGTH | минимальная длина |
| `vC` | COST | минимальная стоимость |
| `vS` | SCORE | минимальный итоговый показатель |

**Дедупликация.** Варианты с одинаковым набором рёбер (`buildSignature`) отсеиваются.

**Ранжирование.** Оставшиеся сортируются по `score` (возрастание). `rank = 1` — лучший. `variant_id` переприсваивается: `v1`, `v2`, `v3`.

**Ограничение:** до трёх содержательно отличающихся вариантов на режим.

### 6.6. Углы поворота и минимальная длина прямого участка

Изменение направления в одной точке — до 90° включительно. Отдельное удорожание поворота не применяется (разъяснение 5). Минимальная длина прямого участка между поворотами отдельно не задаётся. Трасса не содержит необоснованных мелких изломов, зигзагов и ступенчатых фрагментов.

### 6.7. Углы пересечения ограничений

Для **линейной** геометрии (`LineString`, `MultiLineString`) угол пересечения определяется относительно линии ограничения — для `MultiLineString` берётся та конкретная линия, которая реально пересекает трассу в точке входа (разъяснение 6).

Для **полигональной** геометрии (`Polygon`, `MultiPolygon`) — в точке входа специального участка относительно границы полигона.

Если для типа ограничения задан минимальный угол (дороги, трамвайные пути), он соблюдается. Если угол не удаётся определить — ребро отклоняется (fail-closed), чтобы гарантировать соблюдение требований.

### 6.8. Наложение специальных проходов

Если специальные проходы накладываются друг на друга:

- На общем фрагменте выполняются все геометрические требования.
- Для стоимости применяется **наибольший** из соответствующих `Kспец`. Коэффициенты не суммируются и не перемножаются.
- При изменении набора пересекаемых ограничений начинается новый участок.

### 7.2. Выбор ДУ

Для каждого участка новой сети определяется расчётный расход = сумма `flow_tph` всех ОКС, расположенных **далее по этому участку** (в направлении к сети).

ДУ выбирается по двум критериям одновременно:

1. Пропускная способность ≥ расчётный расход.
2. Предельная длина ≥ длина непрерывного под-пути с одинаковым расходом, включающего этот участок.

Если минимальный по расходу ДУ не проходит по длине — берётся следующий, удовлетворяющий обоим. Произвольное завышение не допускается.

### 7.3. Предельная длина

Проверяется **отдельно по каждому непрерывному под-пути с одинаковым расходом** (разъяснение 1). Общий участок разветвлённой сети учитывается в каждом соответствующем пути. Длины параллельных ветвей **не суммируются**.

- Камера без изменения ДУ — новый отсчёт **не** начинает.
- Технический узел без изменения ДУ — новый отсчёт **не** начинает.
- Изменение расхода (слияние/разделение потоков) — начинается новый отсчёт.
- Изменение ДУ разрешено только вместе с изменением расхода; нельзя менять ДУ точечно для нового отсчёта предельной длины.

### 7.4. Присоединение к существующей сети

Всегда через тепловую камеру.

**Существующая камера** используется, если:

- Точка присоединения не далее 10 м от существующей `heat_chamber`.
- После подключения к камере будет примыкать не более 4 линейных участков.

Иначе создаётся **новая камера** в выбранной точке существующей сети. Отдельный геообъект `tie_in` **не формируется** (разъяснение 13). Отдельное минимальное расстояние между существующей и новой камерой не задаётся.

### 7.5. Стоимость камер и врезок (Таблица 3.2 ТЗ)

| Наибольший ДУ примыкающих участков | Стоимость новой камеры, руб. |
|---|---|
| 50–200 | 3 000 000 |
| 250–500 | 5 000 000 |
| 600–1000 | 8 000 000 |
| 1200–1400 | 12 000 000 |

**Врезка в существующую камеру** — 5 000 000 руб. за каждый новый линейный участок, заканчивающийся в ней.

Стоимость новой камеры **включает** присоединение к существующей сети. Отдельная стоимость врезки при строительстве новой камеры не добавляется.

### 7.6. Стоимость участков

```
Обычный участок:      C_уч = L · c_нов(ДУ) · K_гл
Специальный участок:  C_уч = L · c_нов(ДУ) · K_гл · K_спец
```

где:
- `L` — длина по горизонтальной проекции в EPSG:32637, м.
- `c_нов(ДУ)` — стоимость строительства, руб./м (таблица 1).
- `K_гл` — коэффициент глубины (в базовом 2D-режиме = 1).
- `K_спец` — коэффициент спецпрохода (таблица 2).

Если параметры по длине меняются, стоимость соответствующих частей рассчитывается отдельно.

### 7.7. Расчёт итоговой стоимости

```
construction_cost  = сумма стоимости участков
                   + стоимость новых камер
                   + стоимость врезок в существующие камеры

unconnected_penalty = Σ (100 000 000 + 500 000 · flow_tph)  по неподключённым

calculated_cost    = construction_cost + unconnected_penalty
```

### 8.2. Расчётный габарит

Линия новой сети в GeoJSON — это **ось пары труб**. Для проверки расстояний учитывается расчётная ширина из таблицы 1:

```
внешняя граница сети = ось ± (ширина / 2)
```

Для полигонального ограничения расстояние измеряется от границы полигона до внешней границы габарита сети. Для линейного — от геометрии ограничения до внешней границы.

Если у ограничения задан собственный габарит, расстояние определяется между внешними границами двух габаритов. Условные габариты:

- Газопровод: 0,40 × 0,40 м, глубина до верха — 2,8 м.
- Силовой кабель: 0,20 × 0,20 м, глубина — 2,7 м.
- Существующая тепловая сеть: габарит по таблице 1, глубина — 3,0 м.

### 8.3. Специальные проходы

Специальный проход выполняется **одним прямым участком**. На границах спецпрохода участок делится. Если граница не совпадает с тепловой камерой или точкой подключения ОКС — создаётся `technical_node`.

**Внутри разрешённого специального пересечения минимальное горизонтальное расстояние не проверяется** (разъяснение 7). При прохождении рядом (без пересечения) расстояние измеряется по правилам п.8.2.

**Наложение спецпроходов.** Если спецпроходы пересекаются:

- На общем фрагменте выполняются все геометрические требования.
- Для стоимости применяется **наибольший** из коэффициентов `K_спец`. Коэффициенты не суммируются и не перемножаются.
- На границах общего фрагмента начинается новый участок.
- Каждое отдельное пересечение одного и того же объекта считается отдельным специальным проходом.

### 8.4. Исключение для ОКС

Полигон `restriction_type = "oks"` — непроходимое препятствие с отступом по таблице. **Исключение:** для полигона, содержащего собственную `oks_connection_point`, допускается один финальный прямой участок от ближайшей к точке границы полигона до самой точки.

Требование отступа к собственному полигону на этот участок **не распространяется**, включая часть в зоне отступа перед границей (разъяснение 3). Остальные ограничения продолжают действовать.

Если в одном полигоне несколько `oks_connection_point` — каждая рассматривается как самостоятельная цель (разъяснение 4).

### 8.5. Типы ограничений из таблицы 2

В обязательной части решения используются типы ограничений, перечисленные в таблице 2 технического приложения. Поддержка иных `restriction_type` не является обязательной (разъяснение 9).

## 9. Дополнительный режим с учётом глубины

Раздел 5 ТЗ. **Не является обязательным.**

### 9.1. Общие принципы

Базовый двумерный расчёт сохраняется. Расчёт с глубиной выполняется как **отдельный режим** и формирует **отдельный набор вариантов**. Результаты двух режимов **не объединяются** в одно ранжирование.

Z-координаты в GeoJSON не требуются. Вертикальное положение задаётся атрибутами `depth_start` и `depth_end`.

**В текущей версии сервиса режим с глубиной не реализован.** Выходная геометрия — двумерная, `depth_start` и `depth_end` передаются как `null`, `K_гл = 1`.

### 9.2. Параметры глубины (при реализации)

- Обычная глубина до верхней границы расчётного габарита — **3,0 м**.
- Минимальная глубина — **0,7 м**.
- Максимальная глубина — не задаётся.
- Дискретный шаг по глубине — не задаётся.
- Максимальный уклон — **0,10 м/м**.
- Для изменения глубины на 1 м требуется не менее 10 м по горизонтали.

### 9.3. Профиль глубины (при реализации)

Профиль состоит из участка спуска/подъёма, участка на постоянной глубине и, при необходимости, участка возврата.

### 9.4. Коэффициент глубины K_гл

При `h ≤ 3,0 м`:

```
K_гл = 1
```

При `h > 3,0 м`:

```
K_гл = 1 + 0,10 · (h − 3)
```

где `h` — глубина до верхней границы расчётного габарита, м.

На участке равномерного спуска/подъёма — среднее арифметическое `K_гл` в начале и конце.

### 9.5. Технические узлы на профиле

Если участок пересекает глубину 3,0 м, в этой точке создаётся `technical_node`, участок делится.

### 9.6. Расчёт длины

Для стоимости и предельной длины используется **длина по горизонтальной проекции** в EPSG:32637.

## 10. Стоимость и ранжирование

### 10.1. Формула ранжирования

```
S = 0,7 · (C / 25 000 000) + 0,3 · (L / 100)
```

где:
- `C` = `calculated_cost`, руб.
- `L` = `new_network_length`, м.

**Чем меньше S — тем лучше вариант.**

### 10.2. Штраф за неподключённые точки

```
Ш = 100 000 000 + 500 000 · G
```

где `G` = `flow_tph` точки подключения, т/ч.

**Неподключение допускается только если сервис не нашёл допустимый маршрут** при соблюдении правил ТЗ. Намеренный отказ от технически доступного подключения для улучшения итогового показателя **не допускается** (разъяснение 15).

### 10.3. Разделение режимов

Базовый 2D-режим и режим с глубиной (при реализации) формируют **отдельные наборы вариантов**. Результаты двух режимов не объединяются в одно ранжирование.

### 10.4. Количество вариантов

В каждом режиме сервис может вернуть **до трёх содержательно отличающихся вариантов**. Небольшое смещение одной и той же трассы отдельным вариантом не считается.

## 13. Troubleshooting

### 13.1. Сервис вернул пустой результат

**Симптом:** в `variant_summary` нет новых `heat_network`, все ОКС в `unconnected_oks_ids`.

**Возможные причины:**
- Все ОКС окружены запретными препятствиями.
- `flow_tph` ОКС превышает пропускную способность максимального ДУ (22 501,9 т/ч).
- Длина пути превышает предельную для ДУ 1400 мм (11 276 м).

**Что проверить:** логи `TaskService` и `RoutingService`.

### 13.2. ОКС подключился, но маршрут выглядит неоптимально

**Причины:**
- Углы препятствий смещены наружу на 10 м.
- Другие маршруты заблокированы.

### 13.3. Ошибка подключения к БД

**Решение:**
```bash
docker compose up -d db
docker ps
```

### 13.4. Ошибка при чтении входного GeoJSON

**Симптом:** задача завершилась со статусом `ERROR`, в логе `"Ошибка парсинга feature"`.

**Возможные причины:**
- Отсутствует `object_type` или `id` в properties.
- Геометрия содержит `null` в координатах.
- Неподдерживаемый тип геометрии.

**Что проверить:** валидность GeoJSON через [geojson.io](https://geojson.io).

### 13.5. Некорректные длины в результате

**Причина:** длина считается в EPSG:32637, а не в градусах WGS84.

### 13.6. Стоимость сильно завышена

**Возможные причины:**
- Большая часть ОКС не подключилась — штраф 100 000 000 + 500 000·G за каждую точку.
- `K_спец` неправильно применён.

**Что проверить:** `unconnected_oks_ids` в `variant_summary`, `unconnected_penalty`.

### 13.7. Задача висит в `PROCESSING` слишком долго

**Возможные причины:**
- Очень большой входной файл.

**Что проверить:** логи `TaskService` — там есть тайминги.

### 13.8. На карте отображаются все варианты сразу

**Причина:** GeoJSON содержит все три варианта (`v1`, `v2`, `v3`).

**Решение:** скачайте результат и отфильтруйте объекты по `variant_id` в QGIS или geojson.io.

### 13.9. Реконструкция существующей сети не выполняется

**Причина:** это соответствует ТЗ (разъяснение 14). Существующие объекты используются как есть.
